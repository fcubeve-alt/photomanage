## 一、已修复（代码）

### P1-3 深度处理阻塞主线程 — ✅ 核实属实，且是本次审计最重要的发现

**核实**：`IngestionCoordinator.runDepthPass` 是 `@MainActor` 类上的**同步**方法，
循环调用 `VisionSignals.enrich`（图像解码 + Vision，实测 105–154 ms/张）再调
`Pipeline.run`。2,000 张 ≈ **4.5 分钟完全冻结的界面**，已越过 iOS watchdog 杀进程的阈值。

**最难堪的部分**：`offMain` 就定义在它上方 60 行，没被调用，而它的注释写着
*"在主线程上就是五分钟的界面冻结，会让整个分批设计做出它要避免的事"*。
**注释描述了正确行为，代码做了相反的事。**

**修复**：改为 `async`，每 25 张一批，带取消；进度按批更新；可恢复性直接来自
`needsClassification` 读目录而非内存游标。`enrich` 声明为 `nonisolated static`——
**以后谁把它挪回主 actor，是编译错误，不是用户手机上的四分钟卡死。**

**为什么以前测不出来**：`PVMCore` 有几百个测试但够不到 App target 的代码；
`PVMUITests` 是独立进程的 UI bundle，不能 `@testable import PVM`。
**根本没有地方能断言 App 层的属性**——所以没人断言。新增 `PVMTests` 单元测试 target
就是补这个洞，`IngestionThreadingTests` 直接断言"工作不在主线程上"。

**未采纳的子建议**：审计建议加 bounded concurrency。**故意不加**——Vision 内部已经并行，
再叠一层会抬高峰值内存，而峰值内存正是 A3（jetsam）要防的东西，且恰好在旧机型上最致命。
串行 + 后台批次是更符合本项目风险取向的选择。

### P0-2 真机验证前禁止写入照片库 — ✅ 核实属实，但成因与审计描述不同

**核实**：全仓库**没有任何 `PHAssetChangeRequest` / `performChanges`**。
所以"本 App 不会删照片"目前是真的——**但它是因为功能没写完才为真**。

这正是本项目最在意的区别：**因缺席而成立的安全属性不是安全属性**。
谁哪天把 `Action.suggestDelete` 接通，保证就无声失效，一个测试都不会红。

**修复**：`LibrarySafety` 把它变成结构性的。
- 所有写入必须经过 `permitWrite`，本 build 一律拒绝并返回可读的理由；
- `mode` 只有满足文档里列的**五项真机验证**才能改，第一项就是 §7 全部容错论证所依赖、
  却从未被观察过的那一条：**删除是否真的进 Recently Deleted、真的能恢复 30 天**；
- `check_no_photo_writes.py` 扫描发布源码，抓绕过闸门的写入；
- 该检查**第一次运行就咬到了自己的注释**——所以现在剥离注释行，并且双向自测
  （真调用必须被抓、注释必须不被抓）。

### P1-4 过宽的照片权限 — ⚠️ 现象属实，但**建议的修法平台不支持**

**现象核实属实**：`.readWrite` 被申请，而 App 一行写入代码都没有。

**但审计的建议无法实现，而且是我先实现了才发现的。**
`PHAccessLevel` 只有两个成员：`.addOnly` 和 `.readWrite`。
**`.addOnly` 是只能写不能读**——它给的是"能往相册里加照片、但看不见任何照片"。
**iOS 根本没有只读的照片权限档位。**一个要读相册的 App 只有一个选择。

我按建议写了 `.read`，**编译器告诉我它不存在**
（`type 'PHAccessLevel' has no member 'read'`，run 34571492681）。
这是我自己的流程失误：我核实了审计的**事实**，却没核实它的**建议**在 API 上是否成立就动手了。

**审计底下的关切仍然成立，从另外三个地方回答：**
1. **App 结构上不能写**——`permitWrite` 拒绝，`check_no_photo_writes.py` 在构建时拦截。
   权限比行为宽，是因为**平台没给更窄的权限**，不是因为行为宽。
2. **`NSPhotoLibraryAddUsageDescription` 确实是多余的，已删**——而且它承诺"恢复 30 天"，
   那是没人在真机上验证过的行为，iOS 却会把这句话显示给用户。
3. **权限弹窗上写清楚**：`NSPhotoLibraryUsageDescription` 末尾加了
   "this version never deletes or changes a photo"——这是用户唯一真正会读的那部分。

### P1-8 本地数据库缺少数据保护设计 — ✅ 核实属实

**核实**：Swift 侧**完全没有** `FileProtectionType`、没有 backup 排除、没有完整性检查。

审计有一句话说得比我们自己的文档准：**目录数据库比它描述的照片更敏感**。
一张护照照片只是几千张里的一张；目录里有它的 OCR 文本、带日期的位置轨迹、
谁在这个人生活里出现过多少次——而且全部建了索引、可搜索。

**修复**：
- `.completeUntilFirstUserAuthentication`——开机后首次解锁前不可读，挡住关机状态下的离线提取。
  **不用 `.complete`**：那会让 `BGProcessingTask` 直接失效（后台跑时手机是锁着的）。
  这是个真实权衡，选了产品需要的那一边，并写明。
- 排除出 iCloud 备份——目录完全可从相册重建，备份它没有收益，却会把 OCR 出来的证件文字送进 iCloud。
- **`-wal` 和 `-shm` 同样处理**。WAL 是最容易被忘记的那个文件，而它装着最近的写入：
  只保护主库等于保护了历史、暴露了今天。

### P1-10 缺少迁移与恢复设计 — ✅ 部分修复

Swift 侧现在写入并读取 `schema_version`，暴露 `needsMigration` 和 `integrityCheck()`。
Python 引擎从第一版就在写，Swift 移植一直没写——所以升级后打开旧库会在第一次查询时炸，
而不是在还能处理的地方。

**写在代码里的一句话**：目录**不含任何原始数据**，每一行都可从相册重算。
所以"删库重建"在这里是最便宜的正确答案，而在大多数 App 里它是个糟糕答案。

## 六、最该记住的一句

审计的结论是：**"研发速度已经超过了项目治理和验证速度。"**

这句话是对的，而且它在本次发现的两个真 bug 上是同一个形状——
**P1-3 是注释描述了代码没有的行为；P1-2/P1-5 是文档描述了仓库没有的状态。**
两者都是"声明"跑在了"被声明的东西"前面。

这个项目一直在追的那个失败模式——*报告的东西从不被它所报告的东西检验*——
现在有了第六个实例，而且是最大的一个：整个状态文档体系报告了一个不存在的仓库，
而唯一在检查它的工具只检查了它是否自洽。

`check_repo_reality.py` 和 `PVMTests` 是这两条的结构性答案。
